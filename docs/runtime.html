Runtime

Turn loop

Each turn ends → the controller snapshots the epoch, counts tool calls, checks background work, then evaluates the condition. not_met sends a continuation steer prompt; for /goal-loop goals met goes to the loop step instead of finishing; otherwise met/impossible finish the goal (src/runtime/controller.ts:690, src/runtime/controller.ts:696).

/goal-loop improvement loop

/goal-loop <objective> is the same machine with a post-met step: the achieved iteration is compacted into a short machine-consumable summary (max(200, maxLoopSummaryTokens) × 4 char cap), the evaluator generates the next goal (single condition, or exactly LOOP_COMPLETE) and arms it under the same rules. Guards: maxLoops (default 5) completed iterations ends as achieved; LOOP_COMPLETE or an unusable generation ends cleanly as achieved; impossible ends the loop as today; zero-tool-call iterations are recorded (loopNotProgress) but never pause; an armed loop never pauses at the turn cap or stall guard either — a one-time warning notice is emitted and the loop keeps running (Esc, a fatal provider error, or /goal clear are the stops); evaluator crashes and planner failures are retried forever (planner failure with backoff, unlimited). Per-iteration info toasts (kind: "loop"), one achieved toast at the end. Loop state (loopEnabled, loopIteration, loopObjective, loopHistory, loopNotProgress, loopCompact) lives on the record and survives restore. A landed compaction re-queues the ground truth as a <goal-loop-reanchor> note so the model recovers the objective, the armed condition and the iteration history (see Compaction).

The verification gate (verifier, not transcriber)

The evaluator model judges the conversation; the plugin can also judge the machine. When evaluator.verifyCommand is set (e.g. "bun run check"), a met verdict is held at the gate: the plugin spawns the command via the user's shell in the goal's directory (bash -c), with evaluator.verifyTimeoutMs (default 600000) as the wall-clock budget, and accepts met only on exit 0. A non-zero exit, a spawn error, or a timeout downgrades the verdict to not_met; the last ~12 lines of combined output ride the reason, so the continuation tells the agent exactly what broke. A missing verifier port is fail-closed (downgraded, never met). Without verifyCommand the behavior is byte-compatible with before; the gate only fires on met. Evidence accepted by the evaluator itself: fresh command output at the current HEAD (after the last change), never prior summaries, the agent's narration, or a previous verdict (src/core/prompts.ts, src/runtime/controller.ts verifyMet, src/index.ts createVerifier).

Running the loop from a fresh session (promotion checklist)

  1. Re-read HEAD first. Every armed /goal-loop iteration is steered to git log --oneline -5, git status --short, git branch --show-current (plus coordinator status --json and git worktree list in a coordinator repo) and the current check output before touching anything. The loop summary is a hint, not ground truth.
  2. Zero-progress is harness-measured. Iterations with zero tool calls (counted by the plugin's own tool events, not by the model's report) increment loopNotProgress; consecutive zero-tool iterations are recorded but never pause the loop. Background-deferred iterations count as real work.
  3. Met is verified. With evaluator.verifyCommand set, the plugin reruns the check on every met verdict before accepting it or arming the next iteration; a looped goal cannot advance on a failed verification.
  4. Probes are read-only. Launch probe/scratch instances with OPENCODE_GOAL_PROBE=1; plugin storage becomes read-only so restore() and friends cannot mutate the live goal records. Point probes at a throwaway checkout; the verification command still executes in the probe's cwd.
  5. Bookkeeping is merge-owned. merge-next unions the live .term/coordinator/state.json with the committed one (live wins per key, mergeLock reset) and auto-commits it on dev as chore(coordinator): record <slug> lease done after merge. Never hand-commit it; never commit to dev directly.
  6. SPEC claims are gated. bun run check runs scripts/spec-check.ts, which fails when the spec-check marker in SPEC.md (files=, tests=) trails npm pack --dry-run --json or the bun test pass count. Update the marker in the same commit that ships the files/tests.

Loop state hygiene on re-arm: the armed iteration resets turns, stall, checkins, verdict, reason, and iterationToolCalls; loopHistory and loopNotProgress carry across iterations on the record.

Auto-compaction

With compactAtTokens > 0, the plugin asks the host to compact the session after a turn when the estimated model-visible context (last assistant input + cache.read + cache.write, src/core/context-size.ts:38) reaches the threshold. An in-flight or recently requested compaction is not re-requested (src/runtime/compactor.ts). Separately, compactOnLoopIteration (default true) requests a host compaction at every /goal-loop iteration boundary — and on restore of a live goal, unless one is already pending or one landed within the last 10 minutes — regardless of the threshold, so the next version arms with a fresh context. Tiny contexts (< 10k estimated tokens) are skipped; the request is queued before the armed synthetic steer; opencode's window-relative auto-compaction remains the backstop. Compaction is never requested mid-work: a turn executing or background subagents/shells running defers both paths (the busy probe fails closed). An accepted boundary request is tracked on the record (loopCompact); landing is evidence-based and never silent: the session.compaction.ended event is authoritative — it records a landing regardless of the size estimate and re-anchors a live loop immediately; or a ≥ 10% drop is observed against the request-time estimate at an arm (surfaced in notices, in /goal output, in the /goal detail dialog and in the jump-row indicator, which carries the miss count while a request is outstanding). A measurable arm with no drop counts a miss; an unmeasurable context never counts as a miss and never a landing — the first unmeasurable arm forces one re-request past the cooldown, repeated unmeasurable arms mark the request staleness unknown (one warning) with at most one forced re-request per 2 arms, never a full suspension. An unlanded request warns once at 2 misses — "compaction did not land; loop is running hot; consider /compact manually" — and re-requests at that arm and every 3rd arm; the 4-miss cap is a backstop only (one final warning at the crossing, then the trickle continues); an arm that just recorded a landing, or that has an unlanded request with fewer than 2 misses, makes no request at all — arms never stack compactions. When a compaction lands on a live loop, the controller also queues a <goal-loop-reanchor> note (delivery: "queue", resume: false) restating the objective, the armed condition, the iteration position and the completed iterations from the record, with the same re-read-the-tree mandate as the arm steer — the lossy summary cannot orphan the armed goal. It never wakes the session and never interleaves into a turn in flight; the next continuation steer carries it into view. Re-anchor notes are coalesced to at most one per session per 2 minutes, so back-to-back landings do not stack. Plain goals rely on the per-turn system reminder instead.

Epoch invalidation

A per-session epoch is bumped by new turns, user prompts, clears, and replaces. Stale async results are dropped (src/runtime/controller.ts:68, src/runtime/controller.ts:1261).

Background defer and idle check-ins

If subagents or background shells still run, evaluation defers and arms check-ins: first after checkinMinutes, then doubling up to 4×. Max idle check-ins default 3 (src/runtime/controller.ts:489, src/runtime/controller.ts:1082, src/core/config.ts:44).
