Runtime

Turn loop

Each turn ends, and the controller snapshots the epoch, counts tool calls, checks background work, then evaluates the condition. A not_met verdict sends a continuation steer prompt. For /goal-loop goals a met verdict goes to the loop step instead of finishing. Otherwise met/impossible finish the goal (src/runtime/controller.ts · evaluate()/finish()).

/goal-loop improvement loop

/goal-loop <objective> is the same machine with a post-met step. The achieved iteration is compacted into a short machine-consumable summary (max(200, maxLoopSummaryTokens) × 4 char cap). Reasoning-control tags (e.g. <ernie:think>) and the duplicated post-tag restart some models emit are removed by a deterministic filter (stripReasoningControl, src/core/sanitize.ts) before the summary persists to loopHistory[].summary and before any history line enters the next-goal prompt; the summarize prompts carry a matching plain-text rule. The evaluator generates the next goal (a single condition, or exactly LOOP_COMPLETE) and arms it under the same rules.

It ends under these guards.

  • maxLoops completed iterations (default 5) end as achieved.
  • LOOP_COMPLETE or an unusable generation ends cleanly as achieved.
  • impossible ends the loop, as today.
  • Zero-tool-call iterations are recorded (loopNotProgress) but never pause.
  • An armed loop never pauses at the turn cap or the stall guard. It emits a one-time warning notice and keeps running. Esc, a fatal provider error, or /goal clear are the stops.
  • Evaluator crashes and planner failures are retried forever. Planner failure backs off, unlimited.

The planner audits candidates in defensive order — broken or weakened gates, stale or contradictory state, behavior without tests, gaps in the constant objective, speed — and arms the highest item whose required work is ABSENT at HEAD. A met verdict may end with one line prefixed next: naming the highest-value remaining improvement (the evaluator's defensive-audit duty); the planner carries that hint forward as a first-class candidate. The line never downgrades a met verdict.

Each iteration fires one info toast (kind: "loop"). The end of the loop fires one achieved toast. Loop state (loopEnabled, loopIteration, loopObjective, loopHistory, loopNotProgress, loopCompact) lives on the record and survives restore. A landed compaction re-queues the ground truth as a <goal-loop-reanchor> note so the model recovers the objective, the armed condition and the iteration history (see Compaction).

The verification gate (verifier, not transcriber)

The evaluator model judges the conversation. The plugin can also judge the machine.

When evaluator.verifyCommand is set (e.g. "bun run check"), a met verdict is held at the gate. The plugin spawns the command via the user's shell in the goal's directory (bash -c), with evaluator.verifyTimeoutMs (default 600000) as the wall-clock budget. It accepts met only on exit 0.

A non-zero exit, a spawn error, or a timeout downgrades the verdict to not_met. The last ~12 lines of combined output ride the reason, so the continuation tells the agent exactly what broke. A missing verifier port is fail-closed (downgraded, never met).

Without verifyCommand the behavior is byte-compatible with before. The gate only fires on met.

The evidence the evaluator accepts is fresh command output at the current HEAD (after the last change), never prior summaries, the agent's narration, or a previous verdict (src/core/prompts.ts, src/runtime/controller.ts verifyMet, src/index.ts createVerifier).

Running the loop from a fresh session (promotion checklist)

  1. Re-read HEAD first. Every armed /goal-loop iteration is steered to git log --oneline -5, git status --short, git branch --show-current (plus coordinator status --json and git worktree list in a coordinator repo) and the current check output before touching anything. The loop summary is a hint, not ground truth.
  2. Zero-progress is harness-measured. Iterations with zero tool calls (counted by the plugin's own tool events, not by the model's report) increment loopNotProgress; consecutive zero-tool iterations are recorded but never pause the loop. Background-deferred iterations count as real work.
  3. Met is verified. With evaluator.verifyCommand set, the plugin reruns the check on every met verdict before accepting it or arming the next iteration; a looped goal cannot advance on a failed verification.
  4. Probes are read-only. Launch probe/scratch instances with OPENCODE_GOAL_PROBE=1; plugin storage becomes read-only so restore() and friends cannot mutate the live goal records. Point probes at a throwaway checkout; the verification command still executes in the probe's cwd.
  5. Bookkeeping is merge-owned. merge-next unions the live .term/coordinator/state.json with the committed one (live wins per key, mergeLock reset) and auto-commits it on dev as chore(coordinator): record <slug> lease done after merge. Never hand-commit it; never commit to dev directly.
  6. SPEC claims are gated. bun run check runs scripts/spec-check.ts, which fails when the spec-check marker in SPEC.md (files=, tests=) trails npm pack --dry-run --json or the bun test pass count. Update the marker in the same commit that ships the files/tests.

Loop state resets on re-arm. The armed iteration resets turns, stall, checkins, verdict, reason, and iterationToolCalls. loopHistory and loopNotProgress carry across iterations on the record.

Storage hygiene

Terminal goal records (achieved/impossible/cleared/failed) are bounded at plugin storage. On restore/startup the controller prunes terminal records past an explicit age cap (30 days, by endedAt, falling back to startedAt) and an explicit per-directory count cap (the newest MAX_TERMINAL_RECORD_ENTRIES = 50 are kept), dropping the oldest first (src/core/types.ts · selectTerminalRecordsToPrune, src/runtime/store.ts · GoalStore.pruneTerminal). Live records (active/paused) and other directories' records are never touched. Terminal records with no usable stamp are kept and reported, not dropped. The prune reports counts only (scanned/pruned/aged/beyond-cap/unstamped-kept) via the log; the dropped records are gone by design. In probe mode (OPENCODE_GOAL_PROBE=1) nothing is removed and the report says so.

Auto-compaction

With compactAtTokens > 0, the plugin asks the host to compact the session after a turn when the estimated model-visible context (last assistant input + cache.read + cache.write, src/core/context-size.ts · estimateContextTokens()) reaches the threshold. An in-flight or recently requested compaction is not re-requested (src/runtime/compactor.ts).

Separately, compactOnLoopIteration (default true) requests a host compaction at every /goal-loop iteration boundary. It happens regardless of the threshold, so the next version arms with a fresh context. Compaction only ever targets the one session whose arm crossed the boundary; a restore of live goals requests nothing and compacts nothing, not even armed loops.

Tiny contexts (< 10k estimated tokens) are skipped. The request is queued before the armed synthetic steer. opencode's window-relative auto-compaction remains the backstop.

Compaction is never requested mid-work. A turn executing or background subagents/shells running defers both paths (the busy probe fails closed).

An accepted boundary request is tracked on the record (loopCompact). Landing is evidence-based and never silent. The session.compaction.ended event is authoritative. It records a landing regardless of the size estimate and re-anchors a live loop immediately. Or a ≥ 10% drop is observed against the request-time estimate at an arm. The landing is surfaced in notices, in /goal output, in the /goal detail dialog, and in the jump-row indicator, which carries the miss count while a request is outstanding.

  • A measurable arm with no drop counts a miss.
  • An unmeasurable context never counts as a miss and never as a landing. The first unmeasurable arm forces one re-request past the cooldown. Repeated unmeasurable arms mark the request staleness unknown (one warning), with at most one forced re-request per 2 arms, never a full suspension.

An unlanded request warns once at 2 misses, with the message "compaction did not land; loop is running hot; consider /compact manually". It re-requests at that arm and every 3rd arm. The 4-miss cap is a backstop only. It emits one final warning at the crossing, then the trickle continues. An arm that just recorded a landing makes no request, and an arm whose outstanding request has fewer than 2 misses makes no request either. Arms never stack compactions.

When a compaction lands on a live loop, the controller also queues a <goal-loop-reanchor> note (delivery: "queue", resume: false). The note restates the objective, the armed condition, the iteration position and the completed iterations from the record. It carries the same re-read-the-tree mandate as the arm steer, so the lossy summary cannot orphan the armed goal. The note never wakes the session and never interleaves into a turn in flight; the next continuation steer carries it into view. Re-anchor notes are coalesced to at most one per session per 2 minutes, so back-to-back landings do not stack. Plain goals rely on the per-turn system reminder instead.

Epoch invalidation

A per-session epoch is bumped by new turns, user prompts, clears, and replaces. Stale async results are dropped (src/runtime/controller.ts · Runtime.epoch, src/runtime/controller.ts · stale()).

Background defer and idle check-ins

If subagents or background shells still run, evaluation defers and arms check-ins. The first fires after checkinMinutes, then the interval doubles up to 4×. Max idle check-ins default 3. The deferral is persisted on the record (waitingSince) and revived on restore, so the ambient pill keeps painting waiting across a restart or plugin reload instead of flipping back to active mid-wait, and the end event of the background work drains it (src/runtime/controller.ts · defer(), src/runtime/controller.ts · checkin(), src/runtime/controller.ts · adoptRestored(), src/core/config.ts · DEFAULTS). A restore does not re-arm the check-in timer; the drain or the next execution boundary clears the restored wait.
