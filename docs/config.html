Configuration

Options live in opencode.json under plugins[].options. Precedence is env var > option > default. Prompts (directive, loopContinuation, summarize*, nextGoal*) live in src/core/prompts.ts.

Set evaluator.verifyCommand for development loops. Without it, the plugin never reruns your check (e.g. bun run check) before accepting a met verdict. An armed dev loop loses the one deterministic guarantee the plugin offers.

Inherit the session's model instead of pinning one. The per-turn verdict always comes from the worker's native evaluator subagent delegation, so it runs on the working session's own model without a separate generation call. evaluator.model now selects the model for the opt-in consensus:2 second vote and the /goal-loop summarize/next-condition steps: set it (or OPENCODE_GOAL_MODEL, or top-level model) to inherit to use the parent session's current model instead of pinning one. The plugin reads the parent session's current providerID/model from the host on each generation, so switching models mid-goal needs no config edit. If the host cannot supply a model (or the sentinel is used in a session without one), the evaluator falls back to session mode rather than failing. A literal provider/model still pins the judge exactly as before.

OPENCODE_GOAL_LEARNING_LOG=0 disables the durable learning/outcome journal (on by default). OPENCODE_GOAL_LEARNING_LOG_PATH=<path> overrides the journal location (default .term/goal-loop/learnings.jsonl, relative to the goal working directory unless absolute). The journal appends one JSONL entry per completed loop iteration and per terminal goal outcome, capturing what happened and a lesson to improve next time. Best-effort: a write failure never throws and never affects goal execution.

OPENCODE_GOAL_LOG_FILE=<path> mirrors every plugin log line to a file as JSON Lines ({"ts","level","message","data"?}), one object per line. The host swallows the plugin's console logger, so this is the only way to see plugin logs from a live session. Best-effort: a logging failure never throws and never affects a commit; the file rotates to <path>.1 once it exceeds 5 MiB (one generation kept). Unset by default.

OPENCODE_GOAL_MIRROR=0 disables the mirror file (on by default): after every changed snapshot the server plugin atomically writes a small owner-only JSON copy of it (<tmpdir>/goal-loop-mirror/<sessionID>.json) which the TUI reads when a re-pull is due and both RPC paths are wedged — see Workstream IX in SPEC.md. The mirror never leaves the machine, is removed when the goal clears, and failing to write it never affects a commit.

Probe mode: OPENCODE_GOAL_PROBE=1 makes plugin storage read-only, so goal records are never written or removed and restore() has no side effects. The verification command still executes in the probe's working directory. Use it for probe or scratch opencode servers. bun run check also runs bun scripts/spec-check.ts (check:spec). It COMPUTES the tarball file count (npm pack --dry-run --json) and the bun test pass count at gate time; nothing is stored in SPEC.md and there is no marker to bump. --write is a no-op for older pipelines.

The defaults table is src/core/config.ts · DEFAULTS. Resolution is src/core/config.ts · resolveConfig. Both env flags OPENCODE_GOAL_REQUIRE_COMMIT and OPENCODE_GOAL_COMPACT_ON_LOOP_ITERATION parse through src/core/config.ts · envBool: 1/true/yes/on are true, 0/false/no/off (all case-insensitive) are false, anything else reads as unset and the option/default applies. Coordinator detection uses src/core/git.ts · detectCoordinator, called from src/core/git.ts · resolveCommitPolicy. Detection holds when both .term/coordinator/config.json and .term/coordinator/state.json exist. It also holds when the coordinator bin exists (project packages/coordinator/bin/coordinator or an absolute plugin bin) and at least one of the two json files does. config.json may set devBranch and worktreeDir. OPENCODE_GOAL_COORDINATOR accepts auto/1/true/yes/on/0/false/no/off (src/core/config.ts · parseCoordinator). Prompts and rubric per mode live in src/core/prompts.ts · coordinatorFlow, src/core/prompts.ts · commitStatusSuffix, src/core/prompts.ts · rubric and src/core/prompts.ts · facts.

Update preferences are ordinary plugin options in the table above (update.channel, update.mode); there is no sidecar file. They are managed with goal-loop channel <main|dev> and goal-loop updates <auto|off>, which rewrite plugins[].options.update in the same config as the pin. Bare /goal-loop is the update trigger — see Install. The checker resolves refs with bin/goal-loop.mjs · resolveLatestRef, reads the pin and options via bin/goal-loop.mjs · readPluginState, and schedules the background check from src/index.ts · scheduleUpdateCheck.
