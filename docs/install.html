Install and use

Viewing these docs

This site is static HTML/CSS with no build step and no internet. Double-click docs/index.html in your file manager, or run xdg-open docs/index.html from the repo root. Keep the whole docs/ folder together. Pages use relative links.

Install

Follow these steps to install and start using goal-loop:

  1. Run the installer

    One line, straight from GitHub:

    curl -fsSL https://raw.githubusercontent.com/paumkim/goal-loop/main/install.sh | sh

    The script puts the goal-loop CLI in ~/.local/bin and runs goal-loop install, which registers the plugin in your OpenCode config as "plugins": ["github:paumkim/goal-loop#v1.2.0"]. No npm account or registry is involved; OpenCode fetches the tag straight from GitHub.

    Requires: OpenCode ≥2.0.29 and node or bun on PATH.

  2. Restart OpenCode and verify

    Restart OpenCode afterwards; the plugin loads on the next start of both the TUI and the server. You can confirm installation with:

    goal-loop status

  3. First run (startup scaffold)

    On plugin bootstrap in a git repository (and safely on every subsequent run), goal-loop provisions an idempotent workflow scaffold. Existing files are never overwritten and only missing pieces are filled in. What a fresh git repo gets:

    • Coordinator/workplace layout: .term/coordinator/config.json, .term/coordinator/state.json, and worktrees/ so the claim → work in wt/<slug> → submit → merge-next flow is ready (when coordinator mode is enabled/auto and the coordinator binary is available).
    • Goal runtime dirs: .term/goal-loop/ (and any configured learning-log parent dir) for runtime artifacts; learnings/state files themselves remain managed as today.
    • Workflow docs/templates (only if absent): SPEC.md (acceptance/verification template), docs/README.md (docs index/maintenance notes), and MAINTAINER.md (where work goes, how it moves, how to finish/merge).
    • Gitignore (append-only): missing rules for runtime/state artifacts (e.g. worktrees/, .term/goal-loop/, coordinator locks/scratch) are appended; existing rules are never removed and tracked workflow docs remain committable.

    Outside a git repository the plugin degrades to runtime-only setup (goal runtime dirs) with a clear log note and never breaks goal arming. If the layout is partial or corrupt, only safe, missing pieces are repaired.

    Factory workflow (short): define acceptance in SPEC.md → claim scope and work in an isolated wt/<slug> worktree/branch → implement and verify with fresh evidence → commit and submit → land via the designated merge step (merge-next in coordinator repos) only after required checks pass. Runtime artifacts stay untracked; workflow/docs changes are tracked.

  4. Use the CLI commands

    goal-loop            # install (default): add the plugin to the OpenCode config
goal-loop uninstall  # remove exactly what install added
goal-loop status     # scope, config path, installed ref, channel, updates
goal-loop update     # check GitHub; repin the plugin when a newer ref exists
goal-loop channel    # main (stable tag) or dev (latest dev commit)
goal-loop updates    # auto (check on bare /goal-loop) or off (never check)

    Updates. Bare /goal-loop checks GitHub and applies any available update; no new slash command is registered, and an immediate toast says the check started. Use /goal for status while checks are on. goal-loop update --check only reports what is available. goal-loop channel main (the default) follows the newest semver tag on GitHub — the most stable option. goal-loop channel dev pins the current dev-branch commit: updates arrive quickly but may break working setups. goal-loop updates off disables all checks, so bare /goal-loop shows loop status again. Preferences are ordinary plugin options — plugins[].options.update = { "channel": "main", "mode": "auto" } in the same config as the pin; there is no sidecar file. An applied update changes only the plugin pin, keeps other options/comments/unrelated keys, backs up the config, and takes effect after you restart OpenCode.

    --global (default) and --project are mutually exclusive. --project targets the current directory's OpenCode config. It searches opencode.json, opencode.jsonc, .opencode/opencode.json, .opencode/opencode.jsonc in that order; the first existing one wins. ./opencode.json is created when none exists. --dry-run prints what would change and writes nothing.

  5. Uninstall if needed

    goal-loop uninstall           # plugin entry only; opencode is as it was
goal-loop uninstall --self    # ...and delete the CLI script itself
goal-loop uninstall --restore # put the pre-install backup back over the config

    Removes exactly what the installer added (the github:paumkim/goal-loop#v1.2.0 entry in plugins). A config file the installer created is deleted when nothing else remains in it. A file that already existed (a $schema-only or {} config) is restored from its pre-install backup instead. If the plugin entry is already missing and an install-time backup exists (the oldest backup whose content provably lacks the plugin, i.e. the first install-time original), uninstall restores that pre-install config unchanged, after taking a fresh safety backup of the current state. A backup that contains the plugin is never restored automatically. --restore puts the pre-install backup back over the config on demand instead, taking a fresh safety backup first.

What the installer touches

The installer touches one file, the config opencode itself picks. For global installs it uses $XDG_CONFIG_HOME/opencode/opencode.jsonc, or ~/.config/opencode/opencode.jsonc when XDG is unset (opencode.json wins when only it exists; opencode.jsonc is created when neither exists). Every file is backed up before writing (<file>.<yyyy-MM-DD-HH-mm-ss>Z.bak, never overwritten). Only the plugins array is edited. Comments, formatting and unrelated keys survive. The run is idempotent. A second install prints already installed and exits 0. An uninstall with nothing to do prints not installed and exits 0. Writes never leave the target scope, and the installer never opens your config by hand.

Prefer manual install? Run opencode plugin add github:paumkim/goal-loop#v1.2.0, add the same specifier to "plugins": [...] by hand, or point plugins at a local clone: { "plugins": ["/path/to/goal-loop"] }. The installer exists so you do not have to.

Commands

CommandAction
/goal <condition>Set goal and start immediately
/goalShow status
/goal clearRemove goal (aliases: stop, off, reset, none, cancel)
/goal-loop <objective>Set a goal; each achieved goal arms an improved one until maxLoops, LOOP_COMPLETE, an impossible verdict, or clear
/goal-loopCheck GitHub for a plugin update and apply it (use /goal for status; set update.mode: off to make bare /goal-loop show status again)
/goal-loop clearEnd the loop (same aliases as /goal clear)
/goal-loop-<N> <objective>Like /goal-loop, capped at N iterations for this run only (integer 1–1000; /goal-loop=N works too). Invalid counts (/goal-loop-abc, /goal-loop-0, /goal-loop-1001) are called out and the configured limit applies
/goal-loop make the docs site faster and more complete
/goal-loop-188 make the whole release pipeline green

N is an integer from 1 to 1000 and never becomes part of the objective or completion condition (/goal-loop investigate the 12 failing tests keeps the 12 as objective text). A per-run cap overrides maxLoops for that run only. The configured default is never rewritten. A later /goal-loop-12 ... applies only to that new run. The directive also works from a raw prompt line in harnesses that do not know the spelling. The plugin strips the token and applies the count itself (src/core/parse.ts, src/index.ts).

The loop advances only on a met verdict. Each iteration is summarized into a short machine-consumable block, and the evaluator proposes the next goal under a strict contract. Pause reasons and resume rules are the same as /goal, plus the following. An armed /goal-loop never pauses at the turn cap or the stall guard; it emits a one-time warning notice and keeps running. Its stops are Esc, a fatal provider error, or /goal clear. Zero-tool-call iterations are recorded but never pause the loop. The loop keeps arming with a fresh compacted context each version.

/goal bun test passes with 0 failures and no test file is modified

Parsing: src/core/parse.ts · parseGoalCommand().

opencode.json options

{
  "plugins": [{
    "package": "github:paumkim/goal-loop#v1.2.0",
    "options": {
      "evaluator": { "model": "opencode-go/deepseek-v4.1-flash" },
      "maxTurns": 0, "stallTurns": 0, "checkinMinutes": 30,
      "maxRetries": 3, "requireCommit": true, "commitBranch": "dev", "coordinator": "auto"
    }
  }]
}

Full table: Config — the documented defaults and env overrides are implemented by src/core/config.ts · DEFAULTS and src/core/config.ts · resolveConfig, and a docs coverage gate (test/docs-coverage.test.ts) pins every DEFAULTS key and every OPENCODE_GOAL_* variable resolveConfig reads to the page (a removed row fails the build). In coordinator repos (term) coordinator: "auto" (default) switches normal agents to wt/<slug> + submit / merge-next instead of a direct dev commit; true forces it, false disables it. merge-next lands the oldest submitted lease on dev and blocks unless bun run check passes on the merged result (a branch whose merge is the fix for a failing gate is merged, not rejected) (packages/coordinator/bin/coordinator merge-next).

Troubleshooting

Pause reasons

For plain goals, only your interrupt (Esc), or an explicit maxTurns cap you set yourself (default 0 = off), pauses the goal. A message cannot extend the cap until /goal clear or a new goal. An armed /goal-loop does not pause at the maxTurns cap or the stallTurns stall guard; it emits one notice each and keeps running. Terminal provider errors (auth 401/403, credit 402, context 413, model 404, quota exhaustion) fail the goal instead of waiting. Rate or usage limits are retried every 15 minutes, forever. Transient failures use capped exponential backoff, forever. Zero-tool iterations and evaluator crashes never pause (src/runtime/controller.ts, README.md).

Failed recovery

Fatal errors (auth 401/403, credit 402, context 413, model 404) fail the goal (status failed, distinct from cleared). Fix the cause, run /goal again; sending a message does not resume a failed goal (src/core/errors.ts · classifyFailure(), src/runtime/controller.ts · handleFailure()).
